\subsection{Pipeline and workloads}
The pipeline is a typical batch job on Parquet data: it filters orders with a positive amount,
joins them with a customer table (sort-merge join), and aggregates per customer, region and
product category.
It has two shuffle exchanges and writes to a no-op sink, so that output writing does not
affect the times. A synthetic generator creates the data. Three features are varied: data
volume (number of orders), file fragmentation (number of input files) and shuffle volume (the
share of orders that pass the filter, 15\,\% or 85\,\%). Table~\ref{tab:workloads} lists all
workloads. The study workloads use seed 42; the four validation workloads use new seeds and
feature values that were not measured before, including a medium volume of 500K orders.

\subsection{Experiments}
Three preparatory experiments fixed the design and are not used in the analysis: a check that
the workload features really change shuffle volume (E1), an exploratory partition sweep (E2)
and an A2 pilot (E4).

\textbf{E3 (A1, partition tuning).} Each A1 workload was run with 1, 2, 4, 8, 16, 50, 200
and 400 shuffle partitions. The input was cached in memory so that only the shuffle changes
between settings. 160 runs.

\textbf{E5 (A2, compaction).} Each A2 workload was run before and after compaction at 200
partitions. Compaction rewrites the input into $\lceil \text{size}/128\,\text{MB} \rceil = 1$
file. The input was not cached, because compaction changes how files are read. Each block
runs three stages in order: the fragmented run, the compaction job and the compacted run.
90 runs, including 30 timed compaction jobs.

\textbf{E6 (validation).} Each validation workload was run with all eight partition settings
in random order, then compacted, then run once on the compacted data, without caching.
120 runs.

\textbf{Protocol.} Runs were grouped into blocks; within a block every cell is run once, and
the order of workloads (and, for A1 and E6, of partition settings) is shuffled again in every
block (seeds 123, 456 and 789). A1 and A2 used 5 blocks and E6 used 3. Every cell was first run
once without timing, and every measured run was preceded by one discarded warm-up run. In
total, 370 runs were measured.

\subsection{Metrics and analysis}
For each run we recorded the wall-clock time, the summed executor run time, shuffle bytes and
spilled bytes. Each setting is summarized by its median over blocks, with the interquartile
range (IQR) and the coefficient of variation (CV); a cell with CV above 0.2 is marked as noisy.
Times were turned into costs with (\ref{eq:p1})--(\ref{eq:p2}), using the on-demand price of
an Amazon EC2 m6i instance in the Mumbai region, \$0.0505 per vCPU-hour (accessed 23 Oct 2026)
\cite{aws2026ec2pricing}, and $v = 12$ vCPUs for P1. With only 5 blocks, a Wilcoxon
signed-rank test cannot reach $p < 0.0625$, so we report medians, effect sizes and block
bootstrap 95\,\% confidence intervals (10\,000 resamples) instead of $p$-values. To check robustness, we repeated the
analysis with the price halved and increased by half (P1 and P2), and with the slowest run of
each noisy cell removed.
