\section{Problem and Cost Model}
\label{sec:problem}

\subsection{Setting}
A recurring Spark pipeline will run $N$ more times on data with similar features. A workload
$w$ is described by its data volume, the number of files its input is split into, and how much
data it shuffles. Before the next run, the operator can keep the \emph{static} configuration
(200 shuffle partitions, no compaction) or apply one action once:
\begin{itemize}
  \item \textbf{A1, partition tuning} (execution level): change
        \texttt{spark.sql.shuffle.partitions} from 200 to a value chosen for $w$;
  \item \textbf{A2, compaction} (storage level): rewrite the input files of $w$ into fewer,
        larger files.
\end{itemize}
We do not combine A1 and A2, so that the effect of each action can be measured on its own.

\subsection{Total cost and break-even point}
Let $\Crun(a)$ be the cost of one run after action $a$, and $\Copt(a)$ the one-time cost of
applying it. For the static option, $\Copt = 0$ and $\Crun = \Cstatic$. Over $N$ runs,
\begin{equation}
  TC(a, N) = \Copt(a) + N \cdot \Crun(a).
  \label{eq:tc}
\end{equation}
With the saving per run $\Delta(a) = \Cstatic - \Crun(a)$, the optimization break-even point
(OBEP) is the smallest $N$ at which the savings cover the one-time cost:
\begin{equation}
  \Nstar(a) = \left\lceil \Copt(a) / \Delta(a) \right\rceil \text{ if } \Delta(a) > 0,
  \quad \text{otherwise } \infty.
  \label{eq:obep}
\end{equation}
An action that saves nothing never pays off; an action whose one-time cost is below one run's
saving pays off at the first run ($\Nstar = 1$).

\subsection{Turning time into cost}
Costs are \emph{estimated} from a published cloud price $p$ per vCPU-hour
\cite{aws2026ec2pricing}; nothing is billed. We use two cost measures (proxies):
\begin{align}
  \text{P1 (machine time):}\quad & C = t_{\mathrm{wall}} \cdot v \cdot p / 3600, \label{eq:p1}\\
  \text{P2 (task time):}\quad & C = t_{\mathrm{exec}} \cdot p / 3600, \label{eq:p2}
\end{align}
where $t_{\mathrm{wall}}$ is the wall-clock time in seconds, $v$ the number of vCPUs reserved,
and $t_{\mathrm{exec}}$ the executor run time summed over all tasks. P1 models paying for a
whole machine while the job runs; P2 charges only for the core time that tasks actually use.
Because $\Copt$ and $\Crun$ use the same proxy, the price $p$ cancels in (\ref{eq:obep}):
$\Nstar$ depends only on measured times.

\subsection{One-time cost of each action}
\textbf{A1.} The best partition count is not known in advance, so it must be found by trying
settings. We charge A1 with a full search: one run at each of the $K = 8$ candidate settings,
$\Copt(\mathrm{A1}) = \sum_{k=1}^{K} C(\text{run at setting } k)$. This is pessimistic, because
search runs also produce output. As a lower bound we also report a \emph{rule-based} variant
where the setting is known without a search, so $\Copt(\mathrm{A1}) \approx 0$.

\textbf{A2.} $\Copt(\mathrm{A2})$ is the measured cost of the compaction job, which reads the
fragmented input and writes a compacted copy. $\Crun(\mathrm{A2})$ is one pipeline run on the
compacted data.

\textbf{Assumptions.} (i) The workload stays similar over the $N$ runs, so a saving measured
once repeats; (ii) $N$ is known from the pipeline's schedule; (iii) new writes do not undo
compaction during the $N$ runs; (iv) evaluating the rule itself costs nothing. $N$ is a model
parameter and is not physically run; we report $N \in \{1, 5, 10, 50\}$.
